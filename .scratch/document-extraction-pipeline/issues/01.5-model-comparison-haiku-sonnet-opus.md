# 01.5: Model comparison — Haiku 4.5 vs Sonnet 5 vs Opus 5

**What to build:** The `FieldExtractor`'s Anthropic implementation now reads its model from the `ANTHROPIC_MODEL` env var (default `claude-opus-5`, set in `.env`). Run the same extraction against the sample documents with `claude-haiku-4-5`, `claude-sonnet-5`, and `claude-opus-5`, and report speed and field-level accuracy for each, to decide whether Opus 5 is actually justified for this task or whether a cheaper/faster model gets the same result.

**Blocked by:** 01 (needs the extraction pipeline, the ACME hand-verified eval, and the `ANTHROPIC_MODEL` seam it introduced)

**Status:** ready-for-agent

- [ ] The eval suite (or a variant of it) runs against all four sample documents once per model (`claude-haiku-4-5`, `claude-sonnet-5`, `claude-opus-5`), driven entirely by `ANTHROPIC_MODEL` — no code changes required to switch models.
- [ ] For each model, report per-document wall-clock latency for the extraction call.
- [ ] For each model, report field-level accuracy against the hand-verified expected values (the same fields the 01 eval checks: Structured Fields exact-match, Natural Language Fields — Burst/TAM — checked for correct substance).
- [ ] Findings are written up (in this file, under a `## Comments` section, or a short report alongside it) comparing the three models on speed and accuracy, with a recommendation on which model the pipeline should default to.
- [ ] `ANTHROPIC_MODEL` in `.env`/README is documented as the way to override the model, whatever the recommendation turns out to be.

## Comments

**Method:** `tests/eval/model-comparison.ts` (`npm run compare-models`) calls `AnthropicFieldExtractor.extract()` directly against all 4 sample documents — no pipeline/Postgres persistence, since Purchase Order routing isn't built yet (issue 02) — timing each call and scoring every Structured Field, Item row, and Special Term (Burst/TAM) against hand-verified expected values (Structured Fields and Items exact-match; Burst/TAM checked for correct substance via keyword pattern, including CloudShield's TAM, which has no such term in its Special Terms and is expected to come back `null`). Selecting the model under test is entirely a matter of setting `ANTHROPIC_MODEL` before each run — the script itself has no per-model branching.

Single run per model, 2026-08-27, real Anthropic API, real sample documents:

| Model | Total latency (4 docs) | Avg latency/doc | Field accuracy | Input $/1M | Output $/1M |
|---|---|---|---|---|---|
| `claude-haiku-4-5` | 19.5s | 4.9s | 120/120 (100.0%) | $1.00 | $5.00 |
| `claude-sonnet-5` | 30.2s | 7.6s | 114/120 (95.0%) | $2.00 | $10.00 |
| `claude-opus-5` | 26.8s | 6.7s | 120/120 (100.0%) | $5.00 | $25.00 |

Per-document breakdown (latency ms, fields matched):

| Document | Haiku 4.5 | Sonnet 5 | Opus 5 |
|---|---|---|---|
| ACME Order Form | 5349ms, 31/31 | 7704ms, 31/31 | 5680ms, 31/31 |
| CloudShield Order Form | 6005ms, 35/35 | 11041ms, 29/35 | 11105ms, 35/35 |
| BrightOps PO | 3860ms, 27/27 | 5446ms, 27/27 | 4900ms, 27/27 |
| NovaFleet PO | 4248ms, 27/27 | 6038ms, 27/27 | 5067ms, 27/27 |

Sonnet 5's only misses were on CloudShield's items: it appended `" (Year 1)"` / `" (Year 2)"` / `" (Year 3)"` to the `productName` for each line (e.g. `"CloudShield Enterprise (Year 1)"` vs. the table's literal `"CloudShield Enterprise"`) — the year comes from a separate column in the source table, not the product name. Not a comprehension failure (the underlying grouping is real), just a formatting choice that fails exact-match; still worth noting since it was the one place a larger/pricier model did strictly worse than both Haiku and Opus.

CloudShield was the hardest document for every model — a 6-page enterprise Order Form with a multi-year pricing table, no explicit TAM term (testing that the model returns `null` rather than hallucinating one from the unrelated "Premium Support" line item), and two conflicting "Customer Billing Name" labels (company name vs. a person) that require picking the company per the domain glossary's Customer definition. All three models handled the null-TAM and customer-name disambiguation correctly.

**Recommendation: default to `claude-haiku-4-5`.** It tied Opus 5 for accuracy (100%) while being both the fastest model tested and 5x cheaper on input / 5x cheaper on output than Opus, and 2x cheaper than Sonnet on both axes. Opus 5's extra cost and latency bought nothing on this task and this sample set. This is a single run against 4 documents, not a statistically robust sample — a real production default should re-run this comparison across a larger/adversarial document set before fully trusting Haiku's accuracy, but on the evidence gathered here, Opus 5 is not justified as the default. `.env`'s `ANTHROPIC_MODEL` has been changed accordingly.
