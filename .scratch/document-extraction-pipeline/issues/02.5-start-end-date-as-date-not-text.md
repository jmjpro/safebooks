# 02.5: `start_date`/`end_date` as `DATE`, not `TEXT`

**What to build:** `so.start_date`, `so.end_date`, `po.start_date`, and `po.end_date` are currently `TEXT` in `schema.sql`, holding whatever `"mm-dd-yyyy"` string `AnthropicFieldExtractor` produced. Change them to `DATE`, and convert the extractor's `mm-dd-yyyy` string to a real date before persisting.

**Blocked by:** 02 (both `so` and `po` tables now exist with this column shape)

**Status:** ready-for-agent

- [ ] `so.start_date`, `so.end_date`, `po.start_date`, `po.end_date` are `DATE` columns in `schema.sql`, not `TEXT`.
- [ ] `so-repository.ts` and `po-repository.ts` convert the extractor's `"mm-dd-yyyy"` string to a value Postgres accepts as a `DATE` (e.g. ISO `yyyy-mm-dd`) before binding it as a query parameter.
- [ ] A value that passes the extractor's `MM_DD_YYYY` regex but isn't a real calendar date (e.g. `13-45-2025`, `02-30-2025`) is caught rather than silently inserted — either by the insert-time conversion or by leaning on Postgres's own `DATE` validation and treating the resulting error as a field failure (consistent with the existing retry/`needs_review` handling for invalid fields).
- [ ] Existing eval suites (`tests/eval/purchase-order-happy-path.test.ts`, issue 01's SO happy-path suite, `tests/eval/model-comparison.ts` if it asserts on persisted rows rather than just the extractor's raw output) still pass, comparing the persisted date against the hand-verified expected values in a form that accounts for the type change.
- [ ] A short comment or ADR note records why `DATE` was chosen over `TEXT` (lexicographic string sort/range queries on `mm-dd-yyyy` don't match chronological order; `TEXT` can't reject an invalid calendar date the regex lets through), so it doesn't get reverted as a "simplification" later.

## Comments

Raised during review of issue 02: `TEXT` only "works" today because `MM_DD_YYYY` regex-validates every extracted value before it's assigned, so the column only ever holds `NULL` or a `"mm-dd-yyyy"` string — never garbage. But `mm-dd-yyyy` text doesn't sort or range-query chronologically (`"01-15-2026" < "12-01-2025"` as strings), and the regex doesn't check calendar validity (month/day bounds, leap years). A `DATE` column fixes both for free and is the more natural type for something SafeBooks will likely need to query by range (contract terms expiring soon, burst-period overlap, etc.).
