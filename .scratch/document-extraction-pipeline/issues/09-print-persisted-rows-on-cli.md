# 09: Print persisted DB rows on the command line after a pipeline run

**What to build:** After `npm run pipeline` finishes processing a batch, query and print the `so`/`po` (+ `so_items`/`po_items`) rows it just persisted, so a reviewer running the pipeline can see the actual extracted data without opening `psql` themselves.

**Status:** ready-for-human

## Background

Filed from a conversation about `src/index.ts`'s current output. Today the CLI only logs a one-line summary per file (`filename -> table#id (status)`, e.g. from `runPipeline`'s `results`/`failures`) — it confirms persistence happened and where, but not what was actually extracted. Since this is a take-home assignment a reviewer will run and inspect, showing the real persisted field values inline makes the run more self-evidently correct.

- [x] After the per-file summary loop in `src/index.ts`, fetch the `so`/`po` rows (and their `so_items`/`po_items`) for the IDs collected in this run's `results` — reuse the IDs already available rather than re-scanning the whole table.
- [x] Print them in a simple, readable format (table or JSON) to stdout. Keep this to straightforward query + print — no new abstraction/reporting layer. Use `@visulima/tabular` (npm) for the table rendering rather than hand-rolling column alignment.
- [x] Unclassified/needs-review-with-no-type-row documents (see issue 08) don't have a `so`/`po` row to print — decide how (or whether) those show up in this final dump vs. just staying in the per-file summary line.
- [x] Confirm `README.md`'s usage section still matches actual CLI output after this change (per issue 07).

## Comments

Added `src/persistence/query-persisted.ts` (`fetchPersistedRows`) — takes the `PipelineResult[]` `runPipeline` already returns and re-fetches `so`/`so_items`/`po`/`po_items`/`unclassified_documents` by the ids in that batch (`WHERE id = ANY(...)`), rather than re-scanning whole tables. `unclassified_documents` rows *are* included in the final dump — they're a real persisted row per ADR 0006/issue 05, just without item children, so there's no reason to hide them from the summary the way a doc with no table row at all would need to be.

**Went through three library/format iterations before landing on the final shape:**

1. **`console-table-printer`** (first pass): one wide table per section, one row per record. A multi-line `billing_address` (e.g. NovaFleet's 3-line address) made it render extra blank-looking rows with no id/customer — read exactly like phantom DB records, since the library has no wrap/width-capping option at all, only silent row-splitting on embedded `\n`.
2. **`@visulima/tabular`** in the same "one wide table, one row per record" shape: real `maxWidth`/`wordWrap`/`truncate` support (unlike `console-table-printer`), verified against `cli-table3` first — `cli-table3` has the same wrapping capability via `colWidths`, but hasn't published since May 2024 and needs every one of the 14 columns' widths specified manually to avoid the same overflow. But testing `@visulima/tabular` directly against real data showed a structural problem, not a config one: with 12+ columns (`so`/`po` have 14 including two Natural Language Fields — `burst`, `technical_account_manager` — extracted as verbatim prose per ADR-0002/spec), its terminal-width auto-fit squeezes *every* column to fit, including ones with no `maxWidth` set — even a 2-character `id` header got ellipsis-truncated once the wide columns claimed their share.
3. **Final: mixed layout, per section.** `so`/`po`/`unclassified_documents` (13-14 columns) use one expanded `field: value` block per row (`printSection` in `src/cli/print-persisted-rows.ts`), the same shape `psql`'s `\x` command uses for wide rows. Only 2 columns, so there's no many-column budget fight: the key column gets a pinned `width` (not `maxWidth` — an explicit `width` is never shrunk by the auto-fit, unlike `maxWidth`) sized to the longest field name in the row, so a field name is never itself truncated; the value column wraps via `wordWrap` + `maxWidth: 70`, so long prose (and multi-line addresses — `wordWrap` handles embedded newlines natively, no more manual flattening) reads in full across multiple lines instead of being lossily truncated. `so_items`/`po_items` (6 narrow columns, none of them free text) use `printWideSection` instead — an ordinary one-wide-table-per-section layout, same as attempt 2 above minus the squeeze problem, since 6 short columns never trigger the auto-fit fight. Items genuinely read better as a table (product/qty/price side by side across rows) than as 6 separate 2-column blocks per item — confirmed by comparing both against `printPersistedRowsAsWideTable` below.

`printPersistedRowsAsWideTable` is kept as a second export purely for this kind of side-by-side comparison — everything in the wide-table layout, including `so`/`po`, wired into `preview-persisted-rows.ts`'s `--wide` flag. It's never called from `index.ts`.

`created_at`/`processed_at` (real `Date` objects for pg's `TIMESTAMPTZ` columns) print via `Intl.DateTimeFormat('en-CA', { timeZoneName: 'longOffset' })` as `2026-08-28 GMT+03:00` instead of the verbose default `Date.toString()` — built-in `Intl`, not manual offset-math. `start_date`/`end_date` are untouched — they're plain `yyyy-mm-dd` strings, not `Date` objects, per the custom DATE type parser (`src/db/date-type-parser.ts`, ADR-0005).

Also added `tests/support/preview-persisted-rows.ts` — a manual (not part of `npm test`) dev tool that re-prints whatever's already in the dev DB via the same `printPersistedRows` the CLI uses, so the display formatting itself could be iterated on in ~0.3s without a real (costly, ~50s) Anthropic API run each time.

**Progress logging.** A full `npm run pipeline` run took ~50s (each document is 1-3 real LLM calls) and printed nothing until the very end — the per-file summary loop only runs after `runPipeline` has already returned everything. Added an optional `onProgress?: (message: string) => void` callback threaded through `runPipeline` (`src/pipeline/run.ts`) and `extractWithRetries` (`src/pipeline/retry-extraction.ts`), fired at `Found N document(s)...`, `Processing <file>`, `Querying LLM for <file> (attempt 1/3)`, and `Retrying <file> (attempt N/3)` — i.e. right when each slow step actually starts, not batched at the end. `index.ts` passes `console.log` as the callback; every existing caller (tests, `preview-persisted-rows.ts`) omits it and is unaffected, since it's optional and guarded with `?.()`. Verified the message sequence with a throwaway `ScriptedFieldExtractor` run (no real API calls) rather than an actual Anthropic run.

**`@visulima/tabular` display bug.** `po_items`'s wide table showed rows with a misaligned right border — traced to the library undercounting a "smart" typographic character's display width by 1 column. Verified directly with same-length (7-char) test strings: en dash, em dash, and all four curly quotes are each undercounted by 1; ellipsis renders correctly. LLM extraction routinely produces these (e.g. `Analytics Platform – Enterprise`, filenames like `Purchase Order – BrightOps...`). Worked around by normalizing them to their ASCII equivalent in `formatValue` for display only (`DISPLAY_WIDTH_WORKAROUND` in `print-persisted-rows.ts`) — the stored value and everything else that reads it (`psql`, tests) is untouched.

Tests: `tests/pipeline/print-persisted-rows.test.ts` covers `fetchPersistedRows` against a real test database — one test checks `so`/`so_items` come back correctly for an Order Form with an item, the other confirms the fetch is scoped to the ids passed in (an earlier run's `po` row doesn't leak into a later run's result set). Full unit + pipeline suite passes.
